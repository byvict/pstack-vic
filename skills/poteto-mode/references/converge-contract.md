# Converge contract

GitHub is the source of truth. A local report is an input cache; `publish.ts` reconstructs the reconciliation against the current PR before posting anything. Every round binds the full head, trunk contract commit, stable patch id, verification digest and input fingerprint. The PR cannot edit its own verification policy. A new verification uses a new round id. Publication retries use the same round and evidence.

## Commands

Use Node 24, authenticated `gh`, `git`, and a working `CURSOR_API_KEY`. The Cloud owner and its `start.ts` launcher are retired, and 0.5.0 removes them; [Converge](../playbooks/converge.md) describes the local daemon that replaces them. Until then the Cloud owner's commands are:

```sh
node skills/poteto-mode/scripts/converge/converge-reconcile --repo OWNER/REPO --pr NUMBER --output /tmp/converge/round/report.json
node skills/poteto-mode/scripts/converge/prepare-lane.ts --report /tmp/converge/round/report.json --directory /tmp/converge/round/verifier --lane verifier --role 'pr verifier' --descriptor cursor:grok-4.7@high
node skills/poteto-mode/scripts/runner/pstack-runner --parent codex --provider cursor --model grok-4.7 --effort high --mode read-only --repo OWNER/REPO --pr NUMBER --prompt /tmp/converge/round/verifier/prompt.txt --cwd . --output /tmp/converge/round/verifier/output.json --receipt /tmp/converge/round/verifier/receipt.json
node skills/poteto-mode/scripts/converge/publish.ts --report /tmp/converge/round/report.json --evidence /tmp/converge/round/evidence --lane /tmp/converge/round/verifier/manifest.json
node skills/poteto-mode/scripts/converge/converge-arm --repo OWNER/REPO --pr NUMBER --head FULL_SHA --verdict VERIFIED
```

Use `xhigh` in both the descriptor and runner when the verification is complex or when the owner prompt sets an `xhigh` verifier floor from the model sheet. Omit the lane for CI-only. The owner continues after `publish.ts` returns. It never supplies its own verdict to the publisher.

`start.ts` prints one of two shapes, told apart by `kind`. A launch prints `{ "kind": "launched", ... }` with the fields of the launch receipt, and so do a recorded receipt and a recovered launch, which still return or recover first. `launch.json` stores the receipt without `kind`. For a certified head, `start.ts` launches no owner. It admits the PR without the trunk base check, because a stack child certified under `pre-pr` keeps its parent branch as base, and runs the verdict gate, described under Merge and progress, on the PR head. When the gate refuses, `start.ts` requires a trunk base (`PR base differs from trunk`), so it never launches an owner or writes an intent for a stack child, and takes the launch path. On that path it reads the PR again and checks the head before it writes the launch intent, so a failed check never leaves an intent without an agent. Any gate error other than a refusal, such as a failed GitHub read, fails `start.ts` before it writes an intent. The run then fails where it can be seen instead of launching an owner on a PR that may be certified and armed. When the gate certifies, `start.ts` reads the PR again and refuses when the head moved (`PR head moved`) or when the base is not trunk under a verdict other than `pre-pr` (`PR base differs from trunk`). Otherwise it prints `{ "schemaVersion": 1, "kind": "certified", "repo", "pr", "head", "verdictUrl" }` and exits 0. It makes no Cursor call and writes no launch intent, so it does not need `CURSOR_API_KEY` then.

The Raiz certifies a pushed branch on the local machine before the PR exists. It needs Node 24, authenticated `gh`, `git` and the `grok` CLI; it does not need `CURSOR_API_KEY`. `RUN` is the absolute path of a new run directory under a temp root (`$TMPDIR` or `/tmp`) and outside `WORKTREE`, `WORKTREE` a checkout of the pushed head, `ROUNDS` the number of Ajustador rounds the branch went through (0 to 6), and the contract run here is `{ "name": "suite", "command": "npm test" }`. `--parent` names the Raiz's own harness, `claude` or `codex`. The Raiz records every contract run, chooses the reviewer lane, writes each lane's manifest, runs one `pstack-runner` line per lane that the report names, publishes after `gh pr create` on the same head, and arms with `--pending`:

```sh
node skills/poteto-mode/scripts/converge/converge-certify run --directory RUN --name suite --cwd WORKTREE -- npm test
node skills/poteto-mode/scripts/converge/converge-certify report --repo OWNER/REPO --head FULL_SHA --directory RUN
node skills/poteto-mode/scripts/converge/converge-certify reviewer --directory RUN --parent claude --author-provider claude
node skills/poteto-mode/scripts/runner/pstack-runner --parent claude --provider grok --model grok-4.7 --effort xhigh --mode read-only --prompt RUN/lanes/pre-pr-reviewer/prompt.txt --cwd WORKTREE --output RUN/lanes/pre-pr-reviewer/output.json --receipt RUN/lanes/pre-pr-reviewer/receipt.json
node skills/poteto-mode/scripts/converge/converge-certify assemble --directory RUN --author-provider claude --output RUN/certificate.json --adjust-rounds ROUNDS
node skills/poteto-mode/scripts/converge/converge-reconcile --repo OWNER/REPO --pr NUMBER --output RUN/pr-report.json --execution pre-pr
node skills/poteto-mode/scripts/converge/publish.ts --report RUN/pr-report.json --evidence RUN/evidence --certificate RUN/certificate.json
node skills/poteto-mode/scripts/converge/converge-arm --repo OWNER/REPO --pr NUMBER --head FULL_SHA --verdict VERIFIED --pending
```

Since 0.4.12, `converge-certify certify --repo OWNER/REPO --head FULL_SHA --directory RUN --worktree WORKTREE --parent claude|codex [--sheet PATH] --author-provider PROVIDER[,PROVIDER...] --adjust-rounds ROUNDS [--certifier-worktree PATH] [--lease-by NAME [--lease-pid N] --branch BRANCH] [--config PATH]` runs the report, the reviewer choice and the first four lines as one step. It writes the report and refuses an unmapped surface or any gap of the report, an unreadable `Pstack-Author` trailer included, because a gap refuses assembly anyway. It makes the reviewer choice of `converge-certify reviewer` against the sheet (default `~/.claude/pstack-models.md` or `~/.codex/pstack-models.md` by `--parent`) and launches the chosen lane; it refuses when the hard list has a `requires-proof` entry and the chosen lane is not Grok (`Reviewer risk proof unavailable`), because only a Grok reviewer writes risk proofs in this version (N35). It reads the one lane of the `pre-pr certifier` row, never an alias. All of this happens before it runs anything. It checks that `WORKTREE`, which the runs and the reviewer read, and the certifier worktree are at the head and clean (`Worktree is not at the head`, `Certifier worktree has changes`); a round without runs refuses a bad `WORKTREE` at the `reviewer` step. It launches the certifier, when the report asks for it, beside every contract run at once, and the reviewer after the runs, with the prompt block that `mode` selects, and it writes each lane's prompt and manifest. Before each launch it renews the lease through `converge-local lease` when `--lease-by` is given. Each lane gets one relaunch in the same `RUN` when its receipt is not `complete`, or when a certifier left its worktree moved or changed: the lane directory moves to `RUN/attempts/LANE-K` and `RUN/evidence` is deleted. Before a certifier's relaunch, the script writes its worktree's `git status` and `git diff HEAD` to `worktree-status.txt` and `worktree.diff` in that attempt directory, and returns the worktree to the head (`checkout -f --detach`, `reset --hard`, `clean -fd`, which keeps ignored files such as `node_modules`). It then assembles. Every lane runs through the plugin's `pstack-runner` with a 1800 s timeout. Exit 0 prints the certificate. Exit 1 prints `{ "refused": { "step": "report|runs|reviewer|certifier|assemble", "reason": "..." } }` after it has stopped every lane with `SIGTERM` and waited for every run, and it leaves `RUN` as it is. A usage error prints to stderr. The certifier worktree is the Raiz's to prepare, with the dependencies the repository documents, whenever the contract sets `prePr.certifier`, because the report does not exist yet when the call starts.

The local daemon's sweep job runs the sweeper every `intervalMinutes`, as **Local daemon** below describes. It needs Node 24 and authenticated `gh`:

```sh
node skills/poteto-mode/scripts/converge/converge-sweep --repo OWNER/REPO [--config PATH] [--dry-run]
```

## Certificado

A branch certified before its PR exists uses execution `pre-pr`. The trunk contract accepts it only with a `prePr` block: `runs`, a list of `{ "name", "command" }` with unique names matching `^[a-z][a-z0-9-]{0,39}$`, `certifier`, whether a certifier lane drives the app, and optionally `light`, the light class: `paths`, a list of path patterns validated as `surfaces` are (it may be empty), and `reviewer`, `narrow` (the default) or `none`. The contract is refused for a `light` key outside `prePr` (`A light class belongs in the prePr block`), a pattern that is not a safe relative path (`Unsafe relative path`) and any other `reviewer` (`Invalid enum value`). A contract may omit `verifySkill`, `featureMap` and `evidenceRoot` or set them to `null`, but `certifier: true` needs `featureMap` and `verifySkill`. Without a feature map no feature is selected, so a changed surface stays unmapped. A run command is plain words separated by single spaces. The contract is refused (`Unsafe run command`) for an empty command, a leading, trailing or double space, a control character, or any of `` ' " ` $ | & ; < > ( ) { } * ? [ ] ~ # ! \ ``. `converge-certify run` executes argv without a shell and records the argv joined by spaces, and assembly compares that text with the contract.

`converge-certify run --directory RUN --name NAME [--cwd DIR] -- <argv...>` executes the argv in `DIR` (default: the current directory). It writes `RUN/runs/NAME.log` (stdout, then stderr) and `RUN/runs/NAME.json`: command, exit code, start and end times, log SHA256, `head` (the checkout's `HEAD`, or `null` outside a Git checkout) and `clean` (no change to a tracked file and no untracked file; ignored files do not count). It reads `head` and `clean` before the command starts, exits with the command's code, and records 128 for a signal or a spawn failure. Recording a name again replaces its record. The Raiz passes `--cwd` a worktree at the pushed head and an argv that joins exactly to each contract command. `RUN` must live outside that worktree, or in a path it ignores, because a run record inside it is an untracked file that makes the next run unclean.

`converge-certify report --repo OWNER/REPO --head FULL_SHA --directory RUN [--config PATH]` builds the branch snapshot from the pushed head alone. GitHub's compare of the contract commit and the head supplies the files, the diff and the stable patch id. The trusted feature map selects features from them with the same import walk as for a PR. The round has `pr: 0`, and the snapshot has no body, comment, check or CI gap. The same analysis writes `RUN/report.json`, which `report` never overwrites. `report` refuses a contract without `prePr` (`Repository does not accept local certification`), a branch without changes, and a compare of 300 files or more. A `pre-pr` report has one of three modes, decided in this order. `ci-only`: every changed path is an ordinary document, and no path matches `surfaces` or `riskClasses` and the hard list is empty. `light`: the contract has `prePr.light`, every changed path matches one of its `paths` or the change only bumps dependencies, no path matches `surfaces` or `riskClasses`, and the hard list is empty. `full`: anything else. A change only bumps dependencies when its only files are `package.json` and `package-lock.json`, at the root or in `client/`, each modified in place, and `dependencies.ts` accepts each pair of blobs at the merge base and the head (a patch or minor bump, npm registry only). Both `pre-pr` rounds, branch and PR, decide it the same way and without an author check, because the daemon's trust list already limits who opens the PR; so under `pre-pr` such a change is `light`, never `ci-only`, and keeps its runs. Outside `pre-pr` there is no `light`, and only a Dependabot PR that bumps the root manifests is `ci-only` by dependencies. A `full` report requires the `pre-pr reviewer` lane and adds the `pre-pr certifier` when the contract sets `certifier`. A `ci-only` report requires the reviewer alone. A `light` report requires the reviewer, or no lane when `light.reviewer` is `none`, and never the certifier. The Raiz writes the reviewer's prompt from the **Reviewer (light)** block of `pre-pr-prompts.md` when the mode is not `full`. It records `authors`: the provider of every `Pstack-Author` trailer of the compare's commits (a bare provider name, or a descriptor read for its provider alone, so a model or effort the matrix has since retired still counts), once each and sorted. It records one gap `Unreadable Pstack-Author trailer in commit SHA7` per value whose provider is not in the matrix and per `Pstack-Author` line outside its message's trailer block ([Authorship trailer](provider-dispatch.md#authorship-trailer)). The reading is linear in the message, so a hostile commit message cannot stall the verdict gate that runs it. A compare with more commits than it lists refuses (`Branch compare truncated`).

`converge-certify reviewer --directory RUN --parent <claude|codex> [--sheet PATH] --author-provider PROVIDER[,PROVIDER...]` chooses the reviewer lane. It reads `RUN/report.json` and the `pre-pr reviewer` row of the parent's sheet (`--sheet`, or `~/.claude/pstack-models.md` and `~/.codex/pstack-models.md` by parent), checked by the rule `/setup-pstack` applies (one or more lanes of distinct CLI families the runner launches from the parent, no alias; a row that fails it refuses with `change the model sheet with /setup-pstack`). The author families are the declared list united with `authors`, sorted. The first lane of the row whose family is outside that set is written once to `RUN/reviewer.json` (`schemaVersion` 1, `round`, `descriptor`, `provider`, `model`, `effort`, `authorProviders`, `skipped`) and printed; a second call in the same run directory refuses (`Reviewer choice already made`). When no lane is outside the set, it refuses with `No pre-pr reviewer lane is outside the author families (FAMILIES): the row lists LANES; add a lane of another family with /setup-pstack` and writes nothing. A report whose `lanes` lack `pre-pr reviewer`, a `light` report with `reviewer: none`, takes no choice: `reviewer` refuses it (`Report requires no pre-pr reviewer lane: skip the reviewer choice`) before it reads the sheet, and writes nothing. Before it reads the report or the sheet, it refuses a `--parent` other than `claude` or `codex` (`Unknown parent "PARENT": --parent takes claude or codex, the harness of this session`) and a declared family that is not a provider in `model-matrix.json` (`Unknown author provider: PROVIDER`, as `assemble` does), so a typo never chooses a lane. A missing sheet refuses with `No model sheet at PATH; run /setup-pstack`.

Each lane lives in `RUN/lanes/LANE/`: `manifest.json`, `prompt.txt`, `output.json`, `receipt.json`, and its artifacts under `artifacts/converge/ROUND/LANE/`. A Grok reviewer writes from a `read-only` lane, whose sandbox allows writes only under `~/.grok` and the temp roots (`$TMPDIR`, `/tmp`, `/var/tmp`); a `RUN` anywhere else leaves the lane without a place to write. With Grok CLI 1.0.41, a `read-only` lane wrote a file in `$TMPDIR`, and the same write failed in its checkout and under `$HOME/.codex`. A Claude or Codex reviewer's read-only lane writes no file, so it can return findings in `output.json`, which the runner writes from its final response, but cannot bind a risk proof. The certifier cannot run under that sandbox on macOS: it needs a pty and Chromium, and the profile denies the write on `/dev`, IOKit and `mach-register` (CLI-197, measured 2026-09-25). So the certifier runs `unsandboxed` (Grok `--sandbox off`, decided on 2026-09-25) in a disposable worktree that the Raiz creates at the pushed head and removes afterwards, never in the primary checkout. Its receipt records the worktree's HEAD before and after the lane and its `git status` after (`checkout`, see `provider-dispatch.md`). The Raiz writes the manifest and the lane's `prompt.txt` there before it launches the lane; `prepare-lane.ts` prepares only the Cloud `pr verifier`. The manifest has the keys that `prepare-lane.ts` writes: `round` (the local round), `laneId`, `role`, `descriptor`, `prompt`, `promptDigest` (the prompt's SHA256), `output`, `receipt` and `createdAt` (epoch milliseconds). `prompt`, `output` and `receipt` are paths relative to the lane directory. A receipt whose `startedAt` precedes `createdAt` is refused (`Lane receipt predates dispatch`). A `pre-pr reviewer` is admitted as any CLI family of `model-matrix.json`, at any effort the family selects, and a `pre-pr certifier` as a CLI family whose provider has `unsandboxed: true` in the matrix, `grok` in this version (`Certifier provider PROVIDER has no unsandboxed mode`). Both need a receipt with no remote whose model evidence the matrix accepts for that family: a reported model that matches the family's `reportedModel`, or a pinned argv for a family without one. The model sheet chooses the family; admission never pins one. A reviewer needs a `read-only` receipt. A certifier needs an `unsandboxed` receipt (`Certifier lane must run unsandboxed`) whose `checkout.headBefore` is the round head (`Certifier lane ran on another head`), whose `checkout.headAfter` is still the round head (`Certifier lane changed its worktree`), and whose `checkout.statusAfter` is empty (`Certifier lane left changes in its worktree`). The check sees only what git reports in the worktree. A write elsewhere on the machine, or a change the lane hides from git (`assume-unchanged`, `skip-worktree`, `.git/info/exclude`), leaves no trace in the receipt. The lane's shell sees what `~/.zshenv` exports unless the machine skips those exports when `GROK_AGENT` is set (`provider-dispatch.md`, N27). It is admitted only against a `pre-pr` round with `pr: 0`, and a `pr verifier` is refused on a `pre-pr` round. Local artifacts are read from the lane directory and checked by size, SHA256 and media type, as downloaded ones are.

`converge-certify assemble --directory RUN --author-provider PROVIDER[,PROVIDER...] --output RUN/certificate.json --adjust-rounds N` names the families the Raiz knows wrote the branch, as a comma-separated list: the interactive Raiz passes the providers of the authoring rows that wrote it and its own; the local converge daemon's Raiz passes the union of the authoring rows of the sheet and its own `converge raiz` family. Assembly unions the list with the report's `authors` and records the sorted union as `authorProviders`. When the report's `lanes` list `pre-pr reviewer`, it requires `RUN/reviewer.json` of the same round (`Reviewer choice missing: run converge-certify reviewer`, `Reviewer choice belongs to another round`) with the same union (`Author families differ from the reviewer choice`); a report without that lane needs no choice and reads no `reviewer.json`. Each listed family must be a provider in `model-matrix.json` (`Unknown author provider`), the list cannot be empty, and the output must sit directly in the run directory. `N` is the number of Ajustador rounds the branch went through. It is required and must be an integer from 0 to 6, because the adjust loop stops at six. Assembly runs the branch snapshot and analysis again. It refuses a stale or edited `report.json` (`Reconciliation report changed or is stale`) and a run whose log changed after recording. The contract commit is the trunk tip, so any new commit on trunk after `report` refuses assembly, and any new commit on trunk after `assemble` refuses publication (`Certificate patch or policy differs from the PR`). `report` writes `report.json` only once, so the recovery is a new run directory. So an interactive Pré-PR that meets either refusal because trunk moved (`Reconciliation report changed or is stale`, `Certificate patch or policy differs from the PR`) restarts at its step 1 with a new `RUN`, as [Catch-up](../playbooks/catch-up.md) does. In both modes, every recorded run must be a contract run (`Run NAME is not in the contract`), exit 0, carry the contract command, and have been recorded at the report's head on a clean checkout, and its record file must be named after it (`Run record file name differs from its name`). A `full` or `light` report also needs every contract run recorded (`Required run missing: NAME`); a `ci-only` report may leave any of them unrecorded. Every lane manifest under `RUN/lanes/` is admitted. With a reviewer choice, a `pre-pr reviewer` lane other than the chosen one is refused (`Reviewer lane differs from the chosen lane (LANE, chose DESCRIPTOR)`), and one of any author family too (`Reviewer lane is the same family as an author (PROVIDER); launch the lane converge-certify reviewer chose`). Without one, the report requires no reviewer, so any `pre-pr reviewer` lane is an unexpected lane (`Certificate refused: INCONCLUSIVE: Unexpected independent lane`). The decision must be VERIFIED. An open finding, a missing or unexpected lane, a selected feature without driven coverage, an unproved risk obligation, an unmapped surface (`Changed user surface lacks a trusted feature recipe`) or any other gap refuses the certificate. The certificate is written once and stays in the run directory on the local machine.

The certificate (`schemaVersion` 2) records the local round, `authorProviders`, `runs`, `lanes`, `artifacts`, the decision, `reconcileDigest`, `evidenceDigest`, `coverage`, `adjustRounds` and `toolingRef` `pstack-vic@VERSION`, the plugin version. `runs` lists each recorded run as `run` wrote it. For a `ci-only` report, it then lists each contract run that was not recorded, in contract order, as `{ "name", "command", "skip": "ci-only report" }`. Only a `CI-only` certificate can hold a skipped run. The decision's `displayResult` is `VERIFIED` for a `full` report, `Light` for a `light` one and `CI-only` for a `ci-only` one. A `light` certificate with `reviewer: none` has `lanes: []`, and still records `authorProviders`, the sorted union of the declared families and the report's `authors`, which the publisher checks against the PR's trailers as for any certificate. Each `lanes` entry holds the manifest path, `role`, `provider`, the `model` and `effort` of the manifest's descriptor as the model matrix resolves it, the model that the receipt reports (`reportedModel`, a string or `null`) and `receiptDigest`. `artifacts` lists only the artifacts the evidence binds: for each driven feature, the first PNG and the first text or JSON of its coverage entry, in the order the lane listed them, plus every artifact a risk proof cites; a lane's other artifacts stay on disk unreferenced, so a certificate that drives every Clinext feature stays under GitHub's comment limit (N9). Each entry is `{ "lane", "id", "path", "bytes", "sha256", "mediaType" }`, where `lane` is the lane id and `path` is relative to the lane directory. Assembly reads these fields back from the manifest, receipt and artifact files that lane admission verified, and refuses a receipt or artifact whose bytes changed after admission. The artifacts stay on the local machine; the certificate only references them.

After `gh pr create` on the certified head, `converge-reconcile --execution pre-pr` builds the PR report. Under `pre-pr`, the PR snapshot does not read CI: it reads no Tests workflow run, job or log and no check run. The PR report carries no CI state (`checks: []`), so checks that move from queued to done after `gh pr create` cannot make publication refuse. CI test-runner sources stay out of the policy digest, so the PR round's `verificationDigest` equals the branch round's. The PR round also reads the changed files and the diff from GitHub's compare of the trunk contract commit and the head, through the same function as the branch round, and never from `gh pr diff` or the PR's file list, which start at the PR base. So both rounds derive the stable patch id from one source whatever the PR base is, and the compare's limit applies to both: 300 files or more refuse (`Branch compare truncated`). Publication of a `pre-pr` report admits a PR whose base is not trunk, so a stack child publishes its certificate while its base is the parent branch. Every other execution still refuses such a base (`PR base differs from trunk`), and so does the arm. A `pre-pr` report publishes only through `publish.ts --certificate RUN/certificate.json`. The publisher refuses `--lane` or `--retain` beside a certificate, a certificate with a report of another execution, and a PR body with `check:`, `test:` or `artifact:` claims, because CI is still pending. A `feature:` claim passes only when the certificate covers that feature; otherwise the verdict is `INCONCLUSIVE`. The publisher re-admits the certificate against its round and the live trunk contract. It refuses another head (`PR head differs from certificate`) and another patch, contract, policy digest or config path (`Certificate patch or policy differs from the PR`). It applies the run policy again over the PR report: a `full` certificate edited to drop a required run is refused (`Required run missing: NAME`), and so is a run list that differs from what the policy yields. It re-verifies every run, lane and artifact from bytes. It refuses a run added, re-recorded or edited after assembly, a lane or artifact that differs from its certificate entry, a reviewer of any listed author family, and an evidence digest that differs. It re-reads `RUN/report.json` and refuses one whose digest or round differs from the certificate's (`Certificate report differs from the recorded report`). It derives the coverage and the decision again from that report and the admitted lanes, and refuses a certificate whose `coverage` or `decision` differs (`Certificate coverage differs from the admitted lanes`, `Certificate decision differs from the admitted evidence`). Every derived field is thus derived again. `adjustRounds` and `toolingRef` are the Raiz's declarations, checked only in format. `authorProviders` is the union assembly recorded: the publisher checks that no `pre-pr reviewer` lane has a listed family and that every `authors` family of the PR report is listed (`Certificate author families miss a Pstack-Author family (PROVIDER)`). The certificate parse refuses a certificate whose `pre-pr reviewer` lane has its `provider` in `authorProviders` (`Reviewer lane is the same family as an author`). The publisher's re-admission runs that parse first, and so does the verdict gate each time it reads the dossier from the comment. The whole certificate rides in the comment, so a certificate with many artifacts can pass GitHub's 65,536-character comment limit; the publisher then refuses (`Verdict comment exceeds GitHub's 65536-character limit (N)`). Every certificate refusal comes before any comment or status is written. The publisher then decides again over the PR report, which now includes the body and comments, so the status is not always VERIFIED. It posts the versioned comment and `verdict` status as for `converge`: `success` and `VERIFIED by converge` for a VERIFIED decision. The dossier carries the PR round and, under `certificate`, the admitted certificate. A `converge` or `verdict-only` dossier carries `certificate: null`, and a dossier that older tooling published without the key reads as `null`. A `pre-pr` dossier must carry a certificate with its own head, evidence digest and coverage, and no other execution can carry one. A certificate of schema 1, published by tooling before 0.3.0, makes the gate fail (`Unknown certificate schema`), so the arm refuses and the sweep disarms; recovery is a new round, as for note N8. A comment edited to list the reviewer's family in `authorProviders` makes the gate fail the same way (`Reviewer lane is the same family as an author`). The certificate's report, runs, receipts and artifacts stay in the run directory, which must stay intact until publication.

`converge-arm` accepts a `pre-pr` dossier as it accepts a `converge` one. The Raiz assembles a certificate at one trunk tip, which is the verdict's contract commit, and publication decides over the PR text of that moment. The certificate's lanes never read PR text. So the verdict gate re-derives a `pre-pr` verdict every time it runs, and publishes nothing. The arm runs the gate on both of its verdict passes, in strict and in `--pending` mode. It builds the PR snapshot under `pre-pr` and stops with an error when that snapshot reads another trunk commit (`Trunk moved during re-derivation`) or other PR text than the gate read (`PR text changed during re-derivation`). It analyzes the snapshot under the verdict's round id. It first refuses when that report requires a lane role that the certificate's `lanes` lacks (`Certificate lacks a lane the policy now requires at trunk tip SHA`), because the retained lanes below stand in for every lane the report requires: without this check, a `light` certificate whose path left the light class, or a tooling version that classifies it `full`, would pass without the reviewer or the certifier. It then refuses when the head, stable patch id or verification digest differs from the verdict's round (`Certificate patch or policy differs at trunk tip SHA`). It then decides again over the current body and comments, with one retained lane per required role, each with the verdict's coverage and risk adjudication, as `publish.ts --retain` builds them. A decision other than VERIFIED refuses (`Certificate is no longer VERIFIED at trunk tip SHA: VERDICT`), so a new `check:` claim or an injection comment refuses and a plain comment passes. With nothing moved, the same report and the retained lanes decide VERIFIED again. The arm adds a step, also returned as `rederived`, that names the re-derivation: `Re-derived the pre-pr verdict at trunk tip SHA`, with `from contract OLD` before `at` when the contract commit differs and `over changed PR text` at the end when the text differs. The re-derivation binds the trunk tip that the gate reads. When protection does not require the branch to be up to date, GitHub can merge at a later tip that nobody re-derives, the same exposure that such protection already accepts for the code. A `converge` verdict still refuses a moved contract commit (`Verdict identity or execution does not authorize merge`) and changed PR text (`PR text changed after verification`), because its verifier read the PR text. For a moved contract commit, the Cloud owner republishes it with `--retain`.

## Evidence and safety

A read-only Cloud lane runs in its own Cloud environment. A `pr verifier` is admitted only as `cursor:grok-4.7` at `high` or `xhigh`, the Cloud verifier's pinned lane. `CLOUD_VERIFIER` in `contract.ts` names it once for admission, `prepare-lane.ts`, `start.ts` and the `pr owner` and `pr verifier` rows of `setup-pstack`, and goes with the cloud removal in 0.5.0; the pre-PR roles stay unpinned. A CLI family is refused (`Role pr verifier runs on a cloud lane, not PROVIDER`), and so is another Cursor family or effort (`Role pr verifier requires cursor grok-4.7 at high or xhigh`). Its receipt must match the selected model and effort, exact prompt/output paths, full head and round. Cursor's `pinned-argv` receipt proves the requested model and parameters, not the model served. The HTTP runner compares the PR's own remote head ref before and after. A push to another PR cannot invalidate this lane. A changed PR head refuses admission.

The trusted feature map names page recipes. A changed client file selects every feature whose page reaches it through relative imports, literal and template-literal `import()` calls and `import.meta.glob` patterns, read at the contract commit. The walk stops at 2000 files or 32 levels, and a larger graph refuses reconciliation. Routes select every feature, and so does a changed shared component that no page reaches. A changed surface that no page reaches stays unmapped and leaves the verdict `INCONCLUSIVE`. Test-only files (`__tests__/`, `__fixtures__/`, `__mocks__/`, `*.test.*`, `*.spec.*`) are not user surfaces. A changed file without a readable patch also leaves the verdict `INCONCLUSIVE`, except a PNG visual baseline under `__screenshots__/`, whose old and new paths both sit in that folder.

GitHub's compare and the PR's file list omit the per-file patch of a large file, while the full diff that the snapshot already reads still holds its hunks. That diff is the compare fetched with `Accept: application/vnd.github.diff` for the branch round and the `pre-pr` PR round, and `gh pr diff` for the other executions. Before any scan, the snapshot fills a missing patch from the file's section of that diff, the one headed `diff --git a/OLD b/NEW`, where `OLD` is the previous path of a renamed file and the same path otherwise. Git does not quote a space, so one header can head two sections. A section therefore fills a file only when its header occurs once in the whole diff and its rename lines name that file: `rename from OLD` and `rename to NEW` for a renamed file, and no rename or copy line for any other. The patch runs from the section's first hunk header to the next section, without the header lines, so the secret, destructive-statement and injection scans read the file. It keeps git's hunks with three lines of context, which GitHub's `patch` can merge into larger hunks. The added and removed lines and their new-file line numbers are the same, but `changed-delete-predicate` also reads context lines, so that rule alone can decide differently on a filled patch. A file absent from the diff, a path that git quotes (a tab, a quote, or a non-ASCII character under the default `core.quotePath`), a header that occurs more than once in the diff, a section whose rename lines name another file, a binary file, and a pure rename or mode change are not filled. They keep no patch and stay gaps.

A client file that the contract commit lacks, whether added or the new path of a rename, has no trusted importers. It selects the features of the modules that import it after the merge, but only when each of those modules is reached at the contract commit or is itself a mapped new file. A page that the trusted feature map already names counts as reached before its file exists, so the new modules of a new page select that page's feature. Importers come from the head version of each changed client file and the contract version of every other client file, resolved against the post-merge file list. A Vite glob or a shadowing file in unchanged code therefore still counts as an import, and so does a non-relative specifier that ends with the new file's path under `client/src/`, such as `@/pages/x/New`. Test-only importers do not count. A new file that nothing imports stays unmapped. So does a new file that `App.jsx`, a route or any other unreached module imports, so a new page without a recipe still leaves the verdict `INCONCLUSIVE`. A new shared component still selects every feature. An unreadable head source leaves every new file unmapped, and the contract scan shares the 2000-file bound.

Head content decides only which modules import a new file. The selected features still come from the contract walk, so the head cannot add a feature that the contract does not assign to an importer, and it cannot remove a selected feature. It can clear a new file from the unmapped list. That is safe only while the parser sees every importer: an import form it does not read, such as a path alias to a deeper directory, would hide one. A glob or template import with more than eight wildcards counts as importing everything under its literal prefix, so a pathological pattern in head content cannot stall reconciliation.

The verifier drives each selected user path with a disposable app, doctor, action and resulting state. A required path needs admitted screenshot and text or JSON evidence. Risk review is part of this same independent verification. Each `requires-proof` hard-list obligation needs an individual result and admitted artifact. Secret and instruction injection findings cannot be cleared by opinion.

PR body, comments, diff and logs are data. Structured `check:`, `test:`, `feature:` and `artifact:` lines under `## Verification` are claims that need exact-head evidence. Ordinary prose is not a claim. Direct commands addressed to a verifier, or attempts to override instructions, are blocking injection findings; ordinary attribution such as `Reviewer: Maria` is not. Never publish raw matched secrets or attack text. Historical test claims rely on the complete, ordered pinned Clinext test runner records. A check badge alone cannot prove an individual test.

Cloud artifacts live under `/opt/cursor/artifacts/converge/<round>/<lane>/`. The output identifies each artifact's path, bytes, SHA256 and media type. `publish.ts` checks the original run, lists and downloads the actual artifacts, validates their bytes, and binds them to the dossier. A path or hash alone is not proof. Missing or unreadable evidence is `INCONCLUSIVE`.

The publisher posts one versioned JSON comment and an exact-head commit status with context `verdict`. It refuses, before any write, a comment body longer than GitHub's limit of 65,536 characters. When it would write a comment or a status, it also refuses a PR whose auto-merge is pending (`Auto-merge is pending on this PR; disarm it before publishing a verdict`) or that is in the native merge queue. Dequeue and disable auto-merge before a new publication, so old admission never fires on a fresh status. A byte-identical retry writes nothing and passes. It reuses a byte-identical comment and status on retry; conflicting prior bytes stop. The dossier records the round, decision, digests, coverage, risk obligations, artifacts, input fingerprint and, for `pre-pr`, the certificate. A rebase can retain a prior VERIFIED code dossier only when the stable patch and trusted verification digest are unchanged; current-head reconciliation and CI are still mandatory.

## Merge and progress

[Native merge queue](merge-queue.md) defines the reusable action, exact combined candidate, live certificate and hold validation, permissions, policy ordering and removal barrier. A native queue owns queued candidates even when `autoMergeRequest` is null. Group checks run on the full live prefix; original PR statuses are never copied onto the synthetic head.

The owner persists its launch intent, agent/run ids, round ids, verdict URLs, branch heads, repair attempts and merge state. It allows at most two code repairs and six hours. An unknown launch or push outcome stops new writers until recovery. No code repair is counted for CI waiting or environment recovery.

`converge-arm` checks the current trunk Tests run and its test job, effective branch protection and branch rules, every required check, the authenticated exact-head verdict and human hold labels. Effective protection is the union of classic branch protection and the branch rules. Classic checks come from the branch summary (`GET /repos/OWNER/REPO/branches/TRUNK`); effective rule checks come from `GET /repos/OWNER/REPO/rules/branches/TRUNK`. Both reads work with `contents: read`, unlike the administrator-only protection endpoint. An unprotected branch contributes no classic checks; an unreadable or malformed response is an error. The trunk contract's optional `tests` block names the Tests workflow (`workflow`, default `Tests`) and the trunk test job (`job`, default `Run test suite`). `verdict` must be required in protection before activation, and `hold` too before a `--pending` arm. The verdict must pass the verdict gate. For a `converge` verdict too, the strict arm now refuses a dossier reconciled against another contract path than its own `--config` (`Verdict was reconciled against another contract path`). It uses squash auto-merge with `--match-head-commit`. A changed head, red check, missing protection, `needs-victor`, or unreadable state refuses merge. In the Cloud owner flow, the owner monitors the pending request and disarms on a new hold, invalid verdict, lost ownership or timeout. A held `verdict-only` proof posts status `error` and never arms.

The verdict gate decides whether the published verdict on a PR head authorizes merge now. A `verdict` status alone never does. `converge-arm` runs the gate on both of its verdict passes and compares the results, `converge-sweep` runs it on every armed PR, and `start.ts` runs it before it exits as certified. The gate refuses at exactly these conditions and certifies otherwise:

1. There is no trusted status. The newest `verdict` status on the head is not `success` and `VERIFIED by converge` (`Latest verdict status is not trusted VERIFIED`), another account posted it (`VERIFIED verdict status was posted by another account: LOGIN`), or it does not link to a comment on this PR (`Verdict status does not link to this PR`).
2. The linked comment is missing from the PR's comments (`Verdict comment is missing from this PR`), or the authenticated account did not write it (`Verdict comment author is untrusted`).
3. The dossier's round does not name this repository, PR and head, is not VERIFIED, or has an execution other than `pre-pr` or `converge` (`Verdict identity or execution does not authorize merge`). Or the dossier was reconciled against another contract path than the caller's (`Verdict was reconciled against another contract path`).
4. A newer publication supersedes the comment (`A newer converge round supersedes this verdict`).
5. The live PR is not open and ready (`PR must be open and ready`), or its head differs from the head being judged (`PR head moved`).
6. For `converge`, the contract commit differs from the trunk tip (`Verdict identity or execution does not authorize merge`), or the PR text changed (`PR text changed after verification`).
7. For `pre-pr`, text was posted at or after the second the verdict comment was created (`Comment after the verdict by LOGIN`, `Review after the verdict by LOGIN`, naming the oldest). It counts every issue comment and review comment by its creation time and every review by its submission time, a review only when it has a body or requests changes, and leaves out publications and the flow's notes (below). An edit of an older comment does not count. The re-derivation reads text only for injections and claims, so without this condition a request in a comment would merge unanswered; the raiz job answers it with a `respond` attempt, whose new verdict is newer than the text (Local daemon).
8. For `pre-pr`, the report at the tip requires a lane the certificate lacks (`Certificate lacks a lane the policy now requires at trunk tip SHA`), the patch or policy differs at the tip (`Certificate patch or policy differs at trunk tip SHA`), or the re-derived decision is not VERIFIED (`Certificate is no longer VERIFIED at trunk tip SHA: VERDICT`).

The flow and the operator comment under the same account. A flow note is a comment by the authenticated account whose body starts with `<!-- converge:note -->`, which every comment the flow posts besides a publication carries (the daemon's hold comment, a Raiz's replies in a `respond` attempt, Babysit's replies), with `The local converge daemon ` (the hold and post-merge comments of 0.4.13 and earlier) or with `@dependabot ` (a command to Dependabot, whose parser wants the command first). Any other text of the account is the operator's, and condition 7 counts it.

Anything else is an error, not a refusal: a failed GitHub read, drift during the re-derivation, a snapshot limit or malformed data, such as a comment without a creation time. The arm refuses on a refusal or an error, and its own catch disarms. The sweep disarms an armed PR on either. `start.ts` launches on a refusal and fails on an error.

`converge-arm --pending` arms before the PR's CI finishes. It refuses a trunk contract whose `requiredChecks` lacks `hold` (`Pending arm requires "hold" in requiredChecks`), because after a pending arm only the required `hold` check stops the merge for a hold label. It does not require a completed exact-head Tests run or a successful required check. It reads the latest check run from each app and the latest legacy status for each required name. When both exist, both must pass; a legacy status alone cannot satisfy an app-bound requirement. A required check whose latest run is queued, in progress, waiting, requested or pending, or that has no run yet, passes, and GitHub holds the merge until the check passes. A latest run, from the app that protection requires, that completed as `success`, `neutral` or `skipped` passes, because GitHub counts all three as passing. The strict arm accepts the same three conclusions and refuses anything else, including no run, a latest run from another app and a run not completed yet (`Required protected check is not successful: NAME`). A required check whose latest run, from the app that protection requires, completed with any other conclusion refuses the pending arm (`Required protected check failed: NAME`). The reader retains app identity for check runs and never substitutes a legacy status creator id for an app id. A matching check from the required app is needed for strict success. Every other gate is the same as without `--pending`: the trunk Tests run and test job (pending is allowed with a native queue; an explicit failure still refuses admission), every contract context in effective protection, the trusted exact-head verdict, an open ready PR on trunk at the given head, and no hold label. The last step reads `gh pr merge --squash --auto --match-head-commit SHA (checks pending)`.

No session monitors a PR after a pending arm: the local daemon owns it (Local daemon), never the harness that opened it, whose own fix would push without the lease and the disarm below and race a daemon Raiz. The Raiz ends at the arm receipt, and `start.ts` launches no owner for a certified head. `converge-sweep` disarms a held PR whose auto-merge is pending, and an armed PR that the verdict gate refuses, and merges an armed PR whose auto-merge stalled. Between an arm and the next sweep, nothing runs the gate again. A PR text change, a comment or review, or a trunk policy change that would make the gate refuse does not stop GitHub's auto-merge, and the next sweep disarms the PR only if it has not merged by then; the watch job wakes the sweep within a minute of a comment, a review or a trunk move. A hold label stops it through the required `hold` check, described below. A push by a writer does not disable GitHub's auto-merge. A head with no `verdict` status cannot merge, because `verdict` is a required context. A commit keeps its statuses, though, so a force-push back to an earlier head of the PR that still carries our `success` status can merge under the later arm without the gate ever judging it. So any writer must disarm before it pushes to an armed PR. Publication also refuses while auto-merge is pending, and the next sweep disarms an armed PR whose head fails the gate.

The `hold` check is the `hold` job of a workflow named `hold`, which pstack-vic keeps in `.github/workflows/hold.yml`. It runs on the `pull_request` types `opened`, `reopened`, `synchronize`, `labeled` and `unlabeled`, with `permissions: {}`, no checkout and no token. Its one step fails with `::error::` while the event's labels include `needs-victor`. A label change starts a new run on the PR head, and the newest run of the check name decides, for GitHub and for the arm. GitHub's auto-merge waits for a required check that has no run yet and for one whose newest run is pending, and merges when every required check passes. A required check whose workflow a `paths` filter skipped stays Pending and blocks the merge forever, and a job that a false `if:` skipped reports Success, which would pass a held PR. So the workflow has neither. Protection requires `hold` from the GitHub Actions app (id `15368`). The check has four limits:

- A hold label added after the arm stops the merge only once its run exists. When every other required check has already passed, GitHub can merge in the seconds before that run appears.
- A hold label removed starts a passing run. An armed PR then merges when its other checks pass, and a PR that the sweep disarmed for the hold is armed again by the next sweep.
- A PR opened before the check was required has no `hold` run until its next label change or push, and stays Pending until then.
- The workflow has no `workflow_dispatch`, and a re-run replays the labels of its original event. To refresh the check, toggle a label or push. Never re-run `hold`, because a re-run of an earlier passing run can pass a held PR.

`converge-sweep` lists the open PRs whose base is trunk, in PR number order. For each PR it reads the trunk contract and the PR live, and decides on those reads in this order:

1. A PR that is no longer open, or whose base is not trunk, is skipped.
2. A PR with a hold label and auto-merge pending or native queue membership is disarmed, with cause `hold label`. A held PR with neither is skipped.
3. A queued PR goes through the verdict gate: a certified one is skipped (`merge queue owns this candidate`), and a refusal or error dequeues it. A PR with auto-merge pending goes through the verdict gate. When the gate certifies, the PR is skipped (`auto-merge already pending`), unless its auto-merge stalled (below). When the gate refuses or fails with an error, the sweep disarms the PR and reports it `refused`, with the reason and the disarm result. Disarming on an error is safe, because the next sweep arms a certified PR again. The gate reads neither trunk health nor protection, so a red trunk disarms nothing. The first sweep after trunk moves past an armed `converge` PR's contract commit disarms that PR. The disarm happens at that sweep, which the local daemon runs every `intervalMinutes`, not when trunk moves. The PR then stays `refused` at every later sweep until its owner republishes with `--retain` and arms again.
4. A draft is skipped.
5. A PR whose head has no trusted VERIFIED `verdict` status, as the gate's first condition defines it, is skipped (`no trusted verdict on head`). A VERIFIED status that another account posted refuses the PR (`VERIFIED verdict status was posted by another account: LOGIN`).
6. Every other PR goes through `converge-arm --pending`, with `--dry-run` when given.

**A stalled auto-merge.** This retry applies only outside the native queue. GitHub's auto-merge can miss a PR. pstack-vic#59 stayed open for 18 minutes with auto-merge pending, every required check passed and the merge state `clean`, and merged within a minute of the first read of the PR by a session; 20 other armed PRs of the two repositories merged 5 to 90 seconds after their last required check passed. An armed PR that the gate certifies is stalled when both of these hold:

- GitHub's `mergeable_state` for the PR is `clean`, `unstable` or `has_hooks`. In those three states `gh pr merge --auto` merges at once instead of enabling auto-merge.
- The latest run of every required check other than `verdict`, from the app that protection names, completed as `success`, `neutral` or `skipped`, and the last of them completed at least 5 minutes ago (`STALL_MINUTES`), by the completion time GitHub gives. The `verdict` status has no run: the gate certified it, and it precedes every arm.

The sweep then runs the arm's command again, `gh pr merge --squash --auto --match-head-commit SHA`, which merges the PR. GitHub still enforces the required checks on that merge, and the head pin refuses a head that moved. This is the only merge the daemon makes itself. It reads no trunk health, as GitHub's auto-merge reads none. The sweep reads the PR back after the command, whether or not the command failed. A merged PR is `merged` (`auto-merge stalled since TIME, merged after the arm command`), where TIME is the completion time of the required check that passed last. A PR closed without a merge is `skipped` (`PR is no longer open`). A PR still open is `refused` (`auto-merge stalled since TIME, still open after the arm command`) and stays armed, because a command that failed says nothing against the PR. Under `--dry-run` the PR is `dry-run` (`auto-merge stalled since TIME, would run the arm command again`). Any other armed PR is left to GitHub: another merge state (`blocked`, `behind`, `dirty`, `unknown`), or a required check with no run, not finished, not passing or without a completion time. The raiz job holds such a PR after 2 hours (Local daemon). The sweep runs every `intervalMinutes` and on a wake, so the command runs between 5 minutes and 5 minutes plus `intervalMinutes` after the last required check passed.

The sweep reports a disarm by what it reads back after it, and it reads the PR back even when the disarm command fails. A hold-label disarm is `disarmed` (`hold label`) when observed. It is `skipped` only when the read taken before the command found auto-merge already off (`hold label, auto-merge already off`), and `refused` when the PR is no longer open (`hold label, PR merged or closed before disarm`) or still armed (`hold label, auto-merge still pending after disarm`). Under `--dry-run` it is `dry-run` (`hold label, would disarm auto-merge`). A disarm the gate causes is always `refused`, with reason `GATE REASON, RESULT`. RESULT is `auto-merge disarmed`, `auto-merge already off`, `PR merged or closed before disarm`, `auto-merge still pending after disarm` or, under `--dry-run`, `would disarm auto-merge`. Any other error on a PR is `refused` with the error, with the live head when the sweep read it, and nothing is armed. When the read of the PR itself fails, the sweep reports the PR `refused` and cannot disarm it. The sweep makes no judgment about code. It posts no comment, and the job that runs it must not comment on an open PR either. A comment changes a `converge` verdict's PR text, and the next sweep would disarm that PR. The job's only comment is the post-merge failure comment, on a PR that already merged (Local daemon). It prints `{ "swept": [{ "pr", "head", "outcome", "reason" }] }`. `outcome` is `armed`, `disarmed`, `merged`, `dry-run`, `skipped` or `refused`. For `armed` and a dry-run arm, `reason` holds the arm's re-derivation step for a `pre-pr` verdict and is empty for a `converge` one. A refused PR does not stop the sweep. The sweep exits 0 when every PR armed, was disarmed for a hold, was merged after a stall, ran dry or was skipped. It exits 1 when any PR was refused, including every disarm the gate causes, when the trunk contract does not load, or when a read outside any per-PR judgment fails, such as the authenticated account or the open PR list. A failure of that last kind writes the error to stderr and nothing to stdout.

A trunk contract that does not load, for any reason, leaves no policy to check an armed PR against. Examples are a removed or invalid `.cursor/converge.json`, a missing trusted file, no active Tests workflow, or a GitHub read of the contract that fails. The sweep then lists the open PRs on the repository's default branch and disarms each one with auto-merge pending or native queue membership. It reports every PR `refused` with `Trunk contract unavailable: MESSAGE`, followed by the disarm result for an armed PR, writes the failure to stderr, and exits 1, even when no PR is open. A contract read that fails for one PR during the sweep gets the fail-safe treatment for that PR only. The failure appears in that PR's reason, not on stderr, and the sweep exits 1 because that PR is refused. When GitHub itself is down, the reads of this fail-safe path fail too, and the sweep exits 1 without a disarm.

A refused certified PR stays refused at later sweeps while its cause stands. After a trusted policy change on trunk, every sweep refuses it until the Raiz certifies it again, and after text posted after its verdict, until a `respond` attempt certifies it again. While trunk is explicitly red, every sweep refuses a certified PR that is not armed yet, until a trunk Tests run passes. Pending trunk CI permits native queue admission; its combined candidate checks remain mandatory. A removed queue candidate needs a certificate published strictly after removal before admission, and a combined failure is repair work on the rejected synthetic head. An armed PR whose gate certifies stays skipped until it merges or its auto-merge stalls. A stack child is certified against trunk, not against its parent. Its branch round compares the trunk tip with the child's head, so its certificate covers the parent's patch and the child's. The child publishes that certificate while its base is the parent branch. The arm still requires trunk, and the sweep lists only PRs whose base is trunk and skips one whose live base is not (`base is not trunk`), so nothing arms the child yet. GitHub retargets the child to trunk when the parent's branch is deleted after the parent merges, by hand or by the repository's automatic deletion of head branches. The next sweep re-derives the child's certificate at the new tip and arms it. A squash merge, a rebase or a later commit of the parent, or another commit on trunk, leaves the child's merge base with trunk where it was, so the child's patch id does not change. Only a rebase of the child moves its head and patch id, and the child then needs a new certificate. A parent commit that the child never picked up stays outside the child's certificate, like any trunk commit the certificate never saw. The policy is read on trunk, so a child whose parent changes a policy file that the child's round reads certifies only after the parent merges. Those files are the feature map, a Recipe the child's change reaches, `.cursor/converge.json`, the verify skill and the Tests workflow. Until the parent merges, the child's page can lack a trusted Recipe (`Changed user surface lacks a trusted feature recipe`), and a certificate built without the parent's policy fails the re-derivation after the merge (`Certificate patch or policy differs at trunk tip SHA`).

## Local daemon

`converge-local` replaces the cloud Automations with three launchd jobs on the operator's Mac. All three run `skills/poteto-mode/scripts/converge/converge-local` under the plugin directory that the configuration names. The sweep and raiz jobs run every `intervalMinutes`, the sweep whatever trunk does, instead of after each trunk Tests run. The watch job runs every 60 seconds and only wakes the other two (below).

`~/.config/pstack/converge-local.json` holds `parent` (`claude` or `codex`: whose model sheet and CLI the Raiz uses), `repos` (a non-empty list of `{ "repo": "OWNER/REPO", "checkout": "/absolute/primary/checkout" }`, in the order the ticks visit them; each checkout must be a git repository), `intervalMinutes` (an integer from 1 to 60, default 10), and optional `pluginDir` (default: the plugin root the command runs from), `stateDirectory` (default `~/Library/Application Support/pstack/converge-local`), `sheetPath` (default: the parent's sheet, `~/.claude/pstack-models.md` or `~/.codex/pstack-models.md`), `logDirectory` (default `~/Library/Logs`) and `trustedAuthors` (absent or null: an empty list). `trustedAuthors` lists the GitHub logins, besides the authenticated account, whose PRs, comments and reviews the raiz job may hand to a Raiz: letters, digits and hyphens, with `[bot]` at the end for an app. The authenticated login is always trusted and need not be listed. A value that is not an array is refused (`Invalid array`), and so is an entry that is not a string (`Invalid trustedAuthors entry`) or not a login (`trustedAuthors entry is not a GitHub login: LOGIN`). Every path in the file must be absolute. JSON never expands `~`, and launchd starts a job in `/`, so a relative path is refused (`KEY must be an absolute path: PATH`).

`converge-local install` refuses a `--config` other than that default file, before it writes anything or calls `launchctl` (`install runs only from the default configuration FILE, not OTHER: the playbooks' converge-local lease commands read the default configuration`). The lease commands of the playbooks and of the Raiz pass no `--config`, so a daemon installed from another file would keep its leases in a `stateDirectory` those commands never read. `install` writes `~/Library/LaunchAgents/com.pstack.converge-sweep.plist`, `com.pstack.converge-raiz.plist` and `com.pstack.converge-watch.plist`. Each runs `<node> <pluginDir>/skills/poteto-mode/scripts/converge/converge-local tick --job <job> --config <file>` through `/bin/zsh -c` at load, and logs stdout and stderr to `<logDirectory>/pstack-converge-<job>.log`. The sweep and raiz jobs also run every `intervalMinutes` and whenever `<stateDirectory>/wake/<job>/` holds a file (launchd's `QueueDirectories`; `install` creates both directories, since launchd watches them from the bootstrap on). The watch job runs every 60 seconds, whatever `intervalMinutes` says, and has no wake directory. `<node>` is the absolute path of the node that ran `install`, and each file sets `PATH` to the `PATH` of the shell that ran `install`. launchd starts a job with a bare system `PATH`, and a non-interactive shell never reads `~/.zshrc`, where nvm puts `node` and `claude`. `zsh -c` starts from the recorded `PATH` and reads `~/.zshenv`, which exports the lanes' token. It is not a login shell, so macOS's `/etc/zprofile` and its `path_helper` never move the system directories ahead of the recorded entries. Before it writes anything, `install` also refuses when `gh` or the parent CLI (`claude` or `codex`) is not an executable file in an absolute directory of that `PATH` (`install needs gh and PARENT on the PATH it gives launchd; missing: NAMES`), and then when the parent's sheet (`sheetPath`) is unreadable or has no valid `converge raiz` row, since the raiz job would exit 1 on every tick (`install needs a valid converge raiz row in SHEET (CAUSE); run /setup-pstack, then install again`). The files hold a snapshot, so run `install` again after `node` or a CLI moves, as a new nvm version does. Run `install` from the installed plugin, `node ~/.claude/plugins/cache/pstack-vic/pstack/<version>/skills/poteto-mode/scripts/converge/converge-local install` for parent `claude` (the same path under `~/.codex/plugins/cache/` for parent `codex`), and leave `pluginDir` unset. The jobs and the Raiz's `--plugin-dir` then run released code, never a working checkout that may be on another branch. Run `install` again after each plugin update to move the jobs to the new version. `install --when-idle` first checks the same preconditions, then holds the lease `<stateDirectory>/leases/install.json` as `install:<pid>`, bound to its pid (another waiting installer's valid lease refuses it: `another install --when-idle is waiting: NAME until ISO`), polls `launchctl list` every two seconds until neither `com.pstack.converge-sweep` nor `com.pstack.converge-raiz` shows a `PID`, for at most three hours (`install --when-idle gave up: LABELS still running at the end of the wait`), and then installs, so its bootout kills no tick and no Raiz; a tick that starts between the last poll and the bootout still dies with it. pstack-vic's `postMerge` starts it detached from the sweep tick that runs the release. Claude Code keeps the older cache directory, so the old version keeps running until then. The Codex cache keeps only the current version, so for parent `codex` the jobs exit 1 on every tick, before touching any PR, until `install` runs again. `install` loads each file into the user's `gui/<uid>` domain with `launchctl bootout` and then `launchctl bootstrap`, and a failed bootstrap stops it with launchctl's output. `uninstall` boots the three labels out and removes the three files; it reads no configuration. `status` prints the configuration, the parsed `converge raiz` row or its error, `ok` or the error of `gh auth status` and of the parent's auth command (`claude auth status --json` or `codex login status`), the valid leases, every ledger, `waiting` (every stall clock, below), `postMerge` (the post-merge state, below), and `lastTick`, the last record of each job (below), or null when that job has not ticked. A state file that does not parse appears as its error.

`converge-local tick --job sweep [--dry-run]` runs `converge-sweep` on each repository, with `--dry-run` when given, and then, for a repository whose trunk contract has a `postMerge` block, the post-merge pass (below) with the contract the sweep read, and for one whose contract loaded without it, the red-trunk look at the trunk tip (below). A repository whose sweep throws is reported with its failure, and the tick goes on. It prints `{ "job": "sweep", "repos": [{ "repo", "swept", "failure", "postMerge", "redTrunk" }] }`, where `postMerge` is the pass's report or null without a block, and `redTrunk` is `{ "commit", "reason", "errors" }` for a contract without a block (`reason` null while the tip is green or pending) or null otherwise, and exits 1 when any sweep failed or refused a PR, or any post-merge pass or red-trunk look reported an error. Each failure (`REPO: CAUSE`), each refused PR (`REPO#PR: refused: REASON`), each post-merge error (`REPO: post-merge: CAUSE`) and each red-trunk error (`REPO: CAUSE`) is also one line on stderr.

The optional `postMerge` block of the trunk contract, `{ "runs": [{ "name", "command" }], "after": "tests" | "none", "linear": true }`, names what the Mac runs after a merge, once per new trunk commit. `linear` is optional and defaults to disabled; `runs: []` is valid. With `linear: true`, the name `linear` is reserved for the final reconciliation step. `runs` has the grammar of `prePr.runs`: a name matching `^[a-z][a-z0-9-]{0,39}$`, a command split on single spaces with no shell metacharacter, and no name twice. An invalid block, like an invalid `prePr`, makes the whole contract fail to load, and the sweep then disarms as described above. `after` defaults to `tests`: a commit runs only once the latest push run of the contract's `tests.workflow` on that commit completed with `success` and its `tests.job` job succeeded on the commit, read as the arm reads a green trunk. With `none` it runs at once. Work that runs on GitHub, such as a tag, a deploy or a package, stays in a push-to-trunk workflow; `postMerge` is for work that needs the Mac, its credentials or its launchd jobs. The daemon runs these commands with the operator's full local permissions, as it runs `prePr.runs`: whoever can write to trunk already has that power.

Linear targets must be full issue or project URLs in `Pstack-Linear:` trailers in the commits of the certified PR head. Add them before certification; changing a trailer changes the head and requires a new certificate. No trailer or no merged PR is a no-op. Editable PR titles and bodies select no targets.

The pass takes the trunk tip from the contract the sweep read, so it reads nothing while trunk stands still. `<stateDirectory>/post-merge/<owner>-<repo>.json` holds `schemaVersion` 1, `repo` and `tip`, the last trunk commit handled. The first pass of a repository stores the tip and runs nothing, so nothing merged before the block existed replays (`note`: `first pass: stored the trunk tip and ran nothing`). A trunk contract that loads without the block deletes that state file (not under `--dry-run`), so a block added back later starts with a first pass instead of replaying the commits since; the ledgers stay as history. When the tip moved, one compare (`repos/R/compare/<stored>...<tip>?per_page=100`) lists the new commits, and the pass walks the first parent from the tip back to the stored tip and handles the commits oldest first. A tip that does not descend from the stored one (a force-push), a compare that lists fewer commits than its `total_commits`, or more than 50 commits fail the pass with `...; delete STATEFILE to start again from the current tip` and store nothing; deleting the file re-anchors at the current tip without replay. A state or ledger file that does not parse fails the pass and names the file (`Invalid post-merge state file FILE: CAUSE`, `Invalid post-merge ledger FILE: CAUSE`). The stored tip advances one commit at a time, each time a commit ends `done`. The queue stops at the first commit that is not done in this pass, and the later commits wait.

A commit waits, with no attempt, while its push Tests run has not completed or does not exist yet (`TESTS has not completed on the commit`). A run that completed without success, a cancelled one included, or a test job that did not succeed, also waits, since a rerun that turns green resumes the queue, but it is an error on every tick (`SHA waits: NAME did not succeed on the commit`), and the first tick that sees it notifies once (red trunk, below). A ready commit gets `git -C <checkout> fetch --quiet origin SHA` and `git -C <checkout> worktree add --quiet --detach RUN/checkout SHA`, where `<checkout>` is the repository's primary checkout, whose working tree and branches are never touched, and `RUN` is `<tmp>/converge-local/post-merge/<owner>-<repo>-<sha8>-<n>-<unix seconds>`, with `n` the number of recorded attempts plus one. A fetch or worktree that fails is an error (`SHA: checkout failed: CAUSE`) and records no attempt, since the machine and not the commit is at fault; the next pass tries again. The runs then start one after another, without a shell, with the worktree as their working directory, stdout and stderr appended to `RUN/<name>.log`, and the tick's environment plus `PSTACK_REPO`, `PSTACK_COMMIT`, `PSTACK_PR` (the number of the merged PR with base trunk among `commits/SHA/pulls`, empty for a direct push), `PSTACK_CHECKOUT` (the primary checkout) and `PSTACK_PLUGIN_DIR`. Each run has 20 minutes of wall time. Past that it gets `SIGTERM`, then `SIGKILL` ten seconds later, and the attempt fails with reason `timeout`. The runs share the tick's process group, so a bootout of the sweep job ends a running command with the tick. The first run that does not exit 0 ends the attempt. Exit 75 (`EX_TEMPFAIL`) is `deferred` (`NAME exited 75`): before successful processing, the next tick tries again for at most 24 hours after the commit's first attempt, and a 75 after that fails (`NAME exited 75 for 24 hours since ISO`). A command that does not start fails (`NAME did not start`, with `exitCode` null), and any other exit fails (`NAME exited N`). When every run exits 0, the commit is `done`. The worktree is removed with `git worktree remove --force` after every attempt; a removal that fails is an error (`SHA: worktree not removed: CAUSE`) and does not change the outcome.

Each attempt is recorded in `<stateDirectory>/post-merge/<owner>-<repo>/<sha>.json`, through a temporary file and a rename, with mode 0600: `schemaVersion` 1, `repo`, `commit`, `pr`, `firstAttemptAt` and `attempts` (`n`, `startedAt`, `endedAt`, `runs: [{ name, exitCode, logFile }]`, `outcome` `done`, `deferred` or `failed`, `reason`, `runDirectory`). A commit with an earlier `done` attempt only advances the tip (`done on an earlier pass`), even after a crash or a later refused manual replay. Without that earlier success, a `failed` commit stops the repository's queue: the stored tip never passes it, and every tick repeats the error `SHA failed: REASON; retry with converge-local post-merge --repo R --commit SHA, retaining the ledger`. When the commit has a merged PR, the attempt that records the failure posts one comment on that PR: `The local converge daemon's post-merge stopped on commit SHA: REASON.`, the runs with their exit codes and log paths, and ``Later trunk commits wait. Retry with `converge-local post-merge --repo R --commit SHA`, retaining the ledger.`` A comment that fails is an error (`SHA: failure comment failed: CAUSE`), and the failure stands. The PR has merged, so the comment changes no text that a verdict the sweep still judges covers. The manual command retries the commit with its dispatch history retained. The comment goes out under the authenticated account, usually the PR's own author, and GitHub notifies no one of their own comment, so after the comment the attempt shows a macOS notification (last paragraph of this section): title `Converge local`, subtitle the repository, body `Post-merge stopped on commit SHA8: REASON (PR #N)`, without the PR part for a direct push. A notification that fails is an error (`SHA: notification failed: CAUSE`), and the failure stands. A command may run twice for one commit, after a crash between its run and the ledger write, or through `post-merge` by hand, so making it idempotent is the project's obligation.

The pass reports `{ "tip", "handled", "note", "commits": [{ "commit", "pr", "outcome", "reason", "ledger", "runDirectory" }], "errors" }`, where `handled` is the tip stored after the pass and a commit's `outcome` is `done`, `deferred`, `failed`, `waiting` (nothing started in this pass) or `dry-run`. With `--dry-run` and no Linear step, the pass writes nothing and starts nothing: a first pass notes `first pass: would store the trunk tip and run nothing`, and otherwise the first ready commit appears as `dry-run`, with its runs as `NAME: COMMAND` joined by `; `. A real pass holds the lease `<stateDirectory>/leases/post-merge--<owner>-<repo>.json` as `daemon:<pid>`, bound to its pid. While another holder's lease is valid, the tick skips the repository's pass with the `note` `post-merge of R is leased by NAME until ISO`. `converge-local post-merge --repo R --commit SHA [--dry-run] [--plan FILE]` runs one attempt on a trunk commit by hand, through the same readiness check, checkout, runs, ledger and comment, whatever the commit's ledger says, as `post-merge:<pid>` under the same lease, and refuses while another holder's lease is valid, with the same message. It refuses a repository outside the configuration (`R is not in the configuration FILE`), a SHA that is not 40 lowercase hex digits (`Expected full commit SHA`), a contract without the block (`R has no postMerge block in its trunk contract`) and a commit the tip does not descend from (`SHA is not a trunk commit: the tip TIP does not descend from it`). It never moves the stored tip: the next tick reads the ledger, and a `done` releases a queue that stopped there. It prints `{ "job": "post-merge", "repo", ... }` with the pass report's fields and exits 1 on an error, a `failed` attempt or a commit that is not ready. `status` lists `postMerge`: for each repository with a state file, `repo`, `tip`, and each commit whose latest attempt is `deferred` or `failed`, plus processed commits with recorded withheld completion. Each entry includes `commit`, `pr`, `outcome`, `reason`, `attempts` and `file`. A recorded withheld completion also exposes `pendingCompletion` with its targets, saved reason and `processingComplete` flag. A rejected manual application does not erase earlier successful processing or block later commits.

`converge-local tick --job raiz [--dry-run]` reads the `converge raiz` row of the parent's sheet first. It exits 1 without reading GitHub on an unreadable sheet, a missing or repeated row, a row with more than one lane, an alias, a lane the matrix does not resolve, or a lane of another provider than the parent (`converge raiz must be native to the PARENT parent, not PROVIDER`). The tick reads the authenticated account once, before the repositories. Then, for each repository in order, it loads the trunk contract (`.cursor/converge.json`) and lists every open PR, lowest number first, and classifies each one with the reads the sweep and the arm make:

- `skipped`: a PR that is not open, a draft, a hold label, a head in a fork (a PR whose head repository is gone counts as one), an author outside the trusted list (`untrusted author: LOGIN`, checked before any read past the PR record), a head branch equal to the contract's `trunk`, a branch with a valid lease of any holder, a VERIFIED `verdict` status from another account, an uncertified PR younger than 30 minutes whose tests check has not completed on the head (`JOB has not completed on the head and the PR is younger than 30 minutes`, where JOB is the contract's `tests.job`; only such a PR pays for that check-runs read, and a completed check with any conclusion ends the wait, since the lease, not the age, keeps the daemon off a branch a session is certifying), a gate refusal that is a race the next tick sees settled (`PR must be open and ready`, `PR head moved`), or a `converge` verdict from the retired cloud. A PR that would otherwise be `pending`, a forced `--kind` included, is also skipped, and held at once (below), when a login outside the trusted list wrote one of its issue comments or review comments (`untrusted commenter: LOGIN`) or one of its reviews (`untrusted reviewer: LOGIN`). The reason names the first such login, looking at issue comments, then review comments, then reviews. The tick runs this check on no other PR.
- `pending` with work `certify` (no trusted VERIFIED `verdict` status on the head, once its tests check completed or the PR is 30 minutes old), `respond` (the gate refuses with `Comment after the verdict by LOGIN` or `Review after the verdict by LOGIN`), `recertify` (any other gate refusal but the two races, since a new certificate cures it: the three stale ones, `Certificate lacks a lane the policy now requires at trunk tip`, `Certificate patch or policy differs at trunk tip` and `Certificate is no longer VERIFIED at trunk tip`, and a missing or superseded verdict comment, a comment another account wrote, an identity or execution that does not authorize, another contract path; or the gate certifies a PR whose base is trunk and whose `mergeable` is `false`, with reason `PR conflicts with trunk`) or `repair` (the gate certifies, and a required check other than `verdict` and `hold`, from the app that protection names, completed with a conclusion other than `success`, `neutral` or `skipped`, the three that GitHub counts as passing). The conflict comes before the checks. `mergeable` is read from the PR itself (`GET pulls/N`); GitHub answers `null` while it computes it, which that read starts, so the PR stays `idle` until a later tick reads `false`. A stack child, whose base is its parent branch, is never `recertify` for a conflict: its conflict is with the parent, which the stack's owner resolves.
- `idle`: every other PR.

The trusted list is the authenticated login followed by `trustedAuthors`, compared without case, as GitHub compares logins. The authenticated account writes the verdict comment that the gate trusts and the daemon's hold comment, so it is always on the list. Any other account that opens, comments on or reviews a PR, `dependabot[bot]` and CI bots alike, must be listed: the tick never launches on a PR that such an account opened, commented on or reviewed. An unlisted author is a silent skip that names the login, since a PR whose author the operator never listed is not the daemon's (pstack-vic's Dependabot PRs). An unlisted commenter or reviewer on a PR with work holds it at once, with the hold comment's last line naming how to end it: `Delete that comment or add LOGIN to trustedAuthors in the daemon's configuration, then remove the hold label; hiding it is not enough, since GitHub still returns hidden text.` (`review` in place of `comment` for a reviewer). The check reads every issue comment, review comment and review that the API returns, and the API still returns a hidden (minimized) comment: hiding an outsider's comment does not end the skip; deleting the comment, or listing the login, does. Listing a bot trusts the text it relays: Dependabot's release notes, changelog and commit subjects, and a workflow bot's echoes. The list therefore bounds who can put text in front of a Raiz without write access to the repository and without a listed bot relaying it. Write access already lets a collaborator push commits to the head branch, edit the PR body, and change the trunk contract and the workflows, so the tick does not check who pushed a commit or edited the body. It checks the PR author, the commenters, the review commenters and the reviewers, with write access or without. The check runs when the tick classifies the PR. Text that someone outside the list posts after that, up to the end of the attempt, can still reach the Raiz; no later tick launches on the PR while that text stays. The hold comment (below) quotes each attempt's `reason`, including the text the Raiz wrote in `outcome.json`, under the authenticated login, so once the hold label is removed that text passes the check too; this is why Catch-up names an injection by the rule it broke and never quotes it.

The tick reads the authenticated account once, before any repository. When that read fails, the tick reports `authenticated account: CAUSE`, visits no repository and exits 1. A failed read, an unparseable creation time, a comment or review without a user login, a corrupt ledger, lease or stall clock file, a lease the daemon cannot take, or a Raiz launch failure (below) is an error for that PR only. A contract or PR list that fails to load is an error for that repository only. The tick goes on after an error for one PR and after an error for one repository. It prints every error in its report and again on stderr, one line each, and exits 1. It launches at most one Raiz per tick, on the first pending PR whose ledger allows an attempt (the caps and the two waits below), and returns after that attempt, so later PRs wait for the next tick. With `--dry-run` it writes no lease, ledger, label or comment and launches nothing: a PR whose caps are spent goes under `held` and the tick moves on, and the first PR it would launch goes under `launched` with `attempt: null` and ends the tick. The tick prints `{ "job": "raiz", "trustedAuthors", "classified", "launched", "held", "errors" }`, where `trustedAuthors` is the trusted list, the authenticated login first, filled once the account loads and empty when it does not. `converge-local run --repo R --pr N [--kind K] [--dry-run]` takes one configured PR through the same path. It refuses a repository outside the configuration (`R is not in the configuration FILE`); a skip stays a skip, an untrusted author included, and `--kind` replaces the classification of a PR that is not skipped, which then still goes through the commenter and reviewer check.

`converge-local tick --job watch [--dry-run]` wakes the other two jobs within a minute of a change on GitHub, without a webhook, which would need a connection into the Mac and would lose the events that arrive while its receiver is down. It makes only GETs with `If-None-Match` (`gh api -i`), never launches a model and never writes to GitHub. For each repository, in parallel, it reads the open PR list (`pulls?state=open&per_page=100`) and the check runs of the trunk tip (`commits/<trunk>/check-runs?filter=all&per_page=100`, where `<trunk>` is the list's `base.repo.default_branch` or, before any PR listed it, the `default_branch` from one read of `repos/<repo>`; the name is kept when the list empties) and of each open PR head, in parallel. A 200 against a stored ETag is a change. The PR list wakes both jobs: it moves on a PR opened, closed or reopened, a head push, a label, a draft flip, and whatever else the list shows (a comment moves `updated_at`, a push to any branch moves the repository's `pushed_at`). The trunk check runs wake the sweep: trunk moved, or a check on it started or ended, and the arm needs a green trunk. A head's check runs wake the raiz job: its tests check completed, which ends an uncertified head's wait, or a required check failed, which is a `repair`. A 304 is unchanged, although gh exits 1 on it: the tick reads the status line gh prints first. A resource read without a stored ETag, on the first tick after `install` or for a head seen for the first time, is stored and wakes nothing. GitHub counts no 304 against the rate limit, so while nothing changes a repository without an open PR costs two gh processes a minute, one with N open PRs costs 2 + N, and neither spends rate limit. The trunk check runs are read with or without an open PR, so the sweep wakes within a minute of a merge's push CI finishing, which the post-merge pass waits for. `<stateDirectory>/watch/<owner>-<repo>.json` holds `schemaVersion` 1, `repo`, `trunk`, `heads` and `etags` (endpoint to ETag) from the repository's last pass that read everything; a closed PR's head drops out of it. A failed gh, an answer other than 200 or 304, or a 200 without an ETag fails the repository: `REPO: PATH: CAUSE` goes on stderr and in the report, the tick exits 1, and it stores no ETag and wakes nothing for that repository, so the next tick sees the same change. A watch file that does not parse is an error for its repository (`Invalid watch file FILE: CAUSE`); the repository then reads everything afresh, as on its first tick, wakes nothing and rewrites the file. The tick leaves its wakes before it stores the ETags, so a failure between the two repeats a wake instead of losing one. A wake is a signal, never data: the woken job reads GitHub itself. The tick prints `{ "job": "watch", "repos": [{ "repo", "reads", "changed", "failure" }], "woken" }` only when it woke a job or failed, so a quiet minute leaves only its `last-tick-watch.json`. With `--dry-run` it always prints, `woken` names the jobs it would wake, and it stores no ETag, leaves no wake and records no tick.

A real tick of any job, not a `--dry-run` and not `run`, ends by writing `<stateDirectory>/last-tick-<job>.json`, `{ "job", "startedAt", "endedAt", "exitCode", "errors", "wakes" }`, through a temporary file and a rename. The watch job's record adds `reads` (the gh calls it made), `changed` (the endpoints that changed) and `woken`, and its `wakes` is always 0. A tick that stops before its report, such as a raiz tick on an invalid sheet row, records that one error.

A wake is a file under `<stateDirectory>/wake/<job>/`. launchd starts the job while that directory holds a file, and a file that lands during a run starts the job once more after it exits, so no wake is lost; `launchctl kickstart` does nothing to a running job and `WatchPaths` may miss a modification, which is why neither is used. `converge-local nudge [--job sweep|raiz]` leaves one wake per job, both by default, named `<milliseconds>-<pid>`, and prints `{ "woken": [{ "job", "file" }] }`; `--job watch` is refused with the usage, since nothing waits on the watch job. Like `lease`, it reads the configuration only for its `stateDirectory` and uses the default one without the file, so a session wakes the daemon whether or not it is configured. A real tick removes its own job's wake files first, before the sheet and before GitHub, and records how many in `wakes`: a file left behind would make launchd start the tick again every ten seconds, a bad sheet row included. A dry run removes none and leaves none. A raiz tick that launched a Raiz, `run` included, leaves a wake for both jobs after the attempt, so the next pending PR does not wait for the interval and the sweep arms what the attempt certified. Pré-PR, Babysit and Shipping nudge both jobs right after they release the lease, and a PR opened by hand can be nudged the same way. The watch job nudges for what nobody on the Mac does, within a minute: a Dependabot PR, a check that completes or turns red, trunk turning green, a hold label removed on GitHub. The interval stays as the net for what the watch job cannot see, such as an open PR past the first 100 of the list or a `verdict` status that a session published without a nudge (a commit status is neither in the list nor a check run), and for a minute whose watch tick failed.

A lease is a file under `<stateDirectory>/leases/`, named after the repository and the branch, that holds `{ "by", "startedAt", "expiresAt", "pid" }`. It is valid until `expiresAt` and, when `pid` is set, while that process exists. `converge-local lease --repo R --branch B [--by NAME] [--ttl HOURS] [--pid N]` takes or renews it (default `--by interactive`, 3 hours, no pid); a renewal keeps `startedAt` and moves `expiresAt`. It refuses another holder's valid lease (`Branch is leased by NAME until ISO`), a pid that is not a positive integer and a ttl that is not positive. `converge-local release --repo R --branch B [--by NAME]` deletes the file when it is absent, no longer valid or held by NAME (default `interactive`), and refuses another holder's valid lease with the same message. `lease` and `release` read the configuration only for its `stateDirectory`. Without the configuration file they use the default state directory, so an interactive session takes leases whether or not the daemon was ever configured; a configuration file that exists must load. A lease file that does not parse is an error that names it (`Invalid lease file FILE: CAUSE`) for every command that reads it. The daemon takes the lease as `daemon:<pid>`, bound to its own pid, for the attempt, and releases it as the same holder after the attempt, even on failure; a failed release is an error for that PR. The Raiz renews that lease with `--by LEASE_BY --pid <pid>` before every lane launch and push, and never releases it. Pré-PR takes the lease as `interactive` before its push and renews it before every lane launch and push. Babysit and Shipping take it before writing to a branch and renew it before every push. Each releases it with `converge-local release`, whose default `--by interactive` is its own holder. Two more leases live in that directory, both bound to their holder's pid: `post-merge--<owner>-<repo>.json`, held by a post-merge pass, and `install.json`, held by `install --when-idle` while it waits.

A ledger is a file under `<stateDirectory>/ledger/<owner>-<repo>/<pr>.json` with `schemaVersion` 1, the repository, the PR, the head, `firstAttemptAt`, `heldAt`, the attempts (`n`, `kind`, `startedAt`, `endedAt`, `outcome`, `reason`, `runDirectory`) and `launchFailures` (`at`, `reason`). A ledger without `launchFailures`, as 0.4.0 wrote it, reads as an empty list. A new head starts a fresh ledger, and so does the hold label being absent after `heldAt`. Before launching, the tick checks the caps. Two attempts with outcome `failed` on the head (`2 failed attempts on head SHA`), three with outcome `deferred` (`3 deferred attempts on head SHA`), even after a `certified` one, or six hours since the first attempt without a `certified` one (`6 hours since the first attempt on head SHA`), hold the PR. When the caps allow an attempt but the latest attempt on the head is `deferred` and ended less than 30 minutes ago, the tick does not launch: the PR appears as `skipped` with `deferred backoff until ISO (30 minutes after the last deferred attempt)`, and the tick moves to the next PR. The hold applies the contract's first hold label, then records `heldAt` in the ledger, then posts one comment, a flow note: `<!-- converge:note -->`, `The local converge daemon stopped on head SHA: REASON.`, the attempt list (`Attempts: none` when the head has none), and `Remove the hold label to let it try again.`, or, for an unlisted commenter or reviewer, the line that names how to end the hold. A failed comment is an error, and the hold stands. After the comment, the hold shows a macOS notification (last paragraph of this section) with title `Converge local`, subtitle the repository and body `Held OWNER/REPO#N: REASON`; a notification that fails is an error (`OWNER/REPO#N: notification failed: CAUSE`), and the hold stands. While the label is on, the tick skips the PR, so a held head gets no second comment and no second notification, and a new head does not resume it. The same check runs right after an attempt is recorded, at the attempt's end time. An attempt is capped at two hours of wall time: the tick sends the Raiz `SIGTERM`, then `SIGKILL` ten seconds later, and records the attempt `failed` with reason `timeout`. A Raiz launch that did not start, or that ended without an accepted outcome, not by the cap, less than two minutes after its start, is a launch failure: a login, a quota or a moved CLI looks like that, and none of them is the PR's fault. The tick records no attempt. It appends the failure to the head's `launchFailures`, with `at` the time the Raiz ended and `reason` the reason a failed attempt would carry, releases the lease, reports `REPO#PR: raiz launch failed: REASON` and exits 1. When that ledger cannot be written, `REPO#PR: launch failure not recorded: CAUSE` comes first in the report, and the launch failure still follows it. When the caps allow an attempt but the head has at least three launch failures since its last recorded attempt (`MAX_LAUNCH_FAILURES`) and the latest one ended less than 60 minutes ago (`LAUNCH_FAILURE_BACKOFF_MINUTES`), the tick does not launch: the PR appears as `skipped` with `N launch failures on head SHA; next launch after ISO (60 minutes after the last)`, the same reason goes under `errors` as `REPO#PR: REASON`, so the tick still exits 1, and the tick moves to the next PR. A launch that fails after the wait adds a failure and starts another hour. To launch sooner once the machine is fixed, delete the PR's ledger file, `<stateDirectory>/ledger/<owner>-<repo>/<pr>.json`: the next tick starts a fresh ledger, which also drops the head's attempts, so the caps count from zero. Otherwise wait out the hour; `run` honours the backoff too. A recorded attempt clears the list, including a `skipped` outcome recorded as `failed`; a `skipped` outcome that records nothing leaves it. A fresh ledger, on a new head or after the hold label is removed, starts with none. After a `skipped` outcome the tick re-reads the PR. When the PR is not open, is a draft, carries a hold label, has a head other than the launched one, or has `trunk` as its head branch (the PR conditions of Catch-up step 1), the skip records nothing. Otherwise it records a `failed` attempt (`skipped without cause: REASON`, with the Raiz's reason). A re-read that fails is an error for that PR, with no attempt. A `deferred` outcome records an attempt that does not count as failed, and a `certified` one closes the six-hour window.

Two stalls hold a PR that the tick does no work on and that does not move, through the same hold. An armed PR whose `pre-pr` verdict the gate certifies, with no required check failed, is stalled with key `armed`: armed with every required check passing, GitHub merges within seconds and the sweep merges the PR that GitHub misses (A stalled auto-merge), so a PR still open is waiting on something that may never come, such as a required check with no run (a `hold` check that never ran on the head) or one that never finishes. After 2 hours (`ARMED_STALL_HOURS`) it is held with reason `auto-merge armed for 2 hours without a merge; GitHub waits on: WAITS`, where WAITS lists each required check other than `verdict` whose latest run, from the app that protection names, is missing (`NAME has no run`), not finished (`NAME has not finished`) or completed without passing (`NAME concluded CONCLUSION`), then `mergeability not computed` while `mergeable` is `null`, or reads `nothing the daemon can see`. A skipped race refusal and a VERIFIED status from another account are stalled with their reason as the key, and after 1 hour (`REFUSAL_STALL_HOURS`) held with reason `the verdict gate refused for 1 hour: REASON`. The clock is a file, `<stateDirectory>/waiting/<owner>-<repo>/<pr>.json`, with `schemaVersion` 1, `repo`, `pr`, `head`, `key` and `since`, written through a temporary file and a rename with mode 0600. The tick writes it the first time it sees the stall, keeps it while the head and the key stay the same, starts it again when either differs, and removes it without reading it for every PR that is not stalled, a held PR included, so removing the hold label starts a fresh clock. Right after it lists a repository's open PRs, a tick that is neither a dry run nor `run` also removes the clock of every PR no longer open, so a PR reopened on its old head starts a fresh one. A clock file that does not parse is an error for its PR (`Invalid stall clock file FILE: CAUSE`). The thresholds come from 30 CI runs on each repository, 4 to 8 minutes on pstack-vic and 8 to 13 minutes on Clinext: 2 hours is nine times the slowest, and after `recertify` took every refusal a new certificate cures, what stays refused is a race that clears within a tick or an anomaly. An error is not a stall, since a GitHub outage would stall every PR, and neither is a certified PR that the sweep does not arm (a red trunk, a missing protection context): a red trunk has its own notification (below), and holding every PR through it would leave the operator removing labels one by one. An outsider's text on a PR with work is a stall of 0 hours, held on the tick that sees it. A dry run lists a PR whose clock has reached its threshold under `held` and writes no clock. Each classified entry of the report carries its stall, when it has one, as `stall: { key, hours, hold, advice }`.

The Raiz is launched from the sheet row: `claude -p --model MODEL --effort EFFORT --permission-mode bypassPermissions --plugin-dir PLUGIN --output-format json` or `codex exec --model MODEL --config model_reasoning_effort="EFFORT" --sandbox danger-full-access --cd CHECKOUT --skip-git-repo-check -`, in the repository's primary checkout, with the prompt on stdin and stdout and stderr appended to `RUN/raiz.log`. `RUN` is `<tmp>/converge-local/<owner>-<repo>-<pr>-<head8>-<n>-<launch unix seconds>`, where `<tmp>` is Node's `os.tmpdir()` (`TMPDIR`, then `TMP`, then `TEMP`, then `/tmp`) and `n` is the number of recorded attempts plus one. A `skipped` attempt that the re-read PR explains records nothing and repeats `n`, so the launch time keeps every `RUN` fresh. Before the launch, the tick creates `RUN`, writes `RUN/prompt.txt` and deletes a stale `RUN/outcome.json`. The prompt names the Catch-up playbook under the plugin directory and the inputs `REPO`, `PR`, `KIND`, `HEAD`, `BRANCH`, `CHECKOUT`, `RUN`, `PLUGIN` and `LEASE_BY`, one per line; a value with a control character is refused (`Unsafe raiz input KEY`). The Raiz writes `RUN/outcome.json`: `schemaVersion` 1, `repo`, `pr`, `head`, `kind`, `outcome` (`certified`, `deferred`, `failed`, `skipped`), `reason`, `verdictUrl`, `arm` (`armed`, `refused`, `not-armed` or null), `adjustRounds` and `runDirectory`. The tick accepts it only when `repo`, `pr`, `kind` and `runDirectory` equal the launched work; `runDirectory` is compared after resolving symlinks on both sides, or as written when either does not resolve, so a canonical `/private/var/…` spelling of a `/var/…` RUN counts. `head` is the final head the Raiz reports, which a repair or a fixer push moves, so it is not compared. Past the two-minute launch-failure threshold, a missing, invalid or foreign outcome is a `failed` attempt: `no outcome: raiz exited N` for a missing file, where a signal death reports 128 plus the signal number, and `no outcome: CAUSE, raiz exited N` otherwise, where CAUSE is the parse error or `outcome for another repo`, `pr`, `kind` or `run`. A CLI that never started is always a launch failure (`no outcome: raiz did not start`). The attempt's own rules are in [Catch-up](../playbooks/catch-up.md): `skipped` only for its step 1 cases, one relaunch per lane in each `RUN/pre-pr-<n>`, relaunched lanes moved under `RUN/pre-pr-<n>/attempts/`, absolute artifact prefixes, the lease renewal with `--pid` before every lane launch and push, and the fetch of trunk with the branch.

A red trunk commit, one whose latest push run of the contract's `tests.workflow` completed without success (a cancelled run included) or whose `tests.job` did not succeed, notifies once. Two places look. The post-merge pass looks at the commit its queue waits on, in a repository whose contract has `postMerge`. The sweep tick looks at the trunk tip, in a repository whose contract loaded without it (Clinext on 2026-09-30, whose trunk went red with no one told): one read of the tip's push runs, and one of the run's jobs when it succeeded. The first look that sees the commit red reads the merged PR of the commit (as `PSTACK_PR` does), writes `<stateDirectory>/red-trunk/<owner>-<repo>/<sha>.json` (`schemaVersion` 1, `repo`, `commit`, `pr`, `reason`, `notifiedAt`), and only then shows the notification, with body `Trunk red at SHA8: NAME did not succeed on the commit (PR #N)`, without the PR part for a direct push. A commit with a record never notifies again, whatever a later look reads. A read or write that fails is an error (`SHA: red trunk not recorded: CAUSE`), shows nothing, and leaves the notification to the next look, so a failure repeats the error, never the notification. A red tip adds no error of its own to the sweep tick: the notification is the signal, and every arm the sweep attempts already refuses on a red trunk. A dry run writes no record and shows nothing, and its `redTrunk` still names the reason.

A notification runs `osascript -e 'display notification "BODY" with title "TITLE" subtitle "SUBTITLE" sound name "Basso"'` with each string's backslashes and double quotes escaped, capped at 10 seconds, after the ledger and the comment, so it never delays them and never changes an outcome. It goes out once per recorded post-merge failure, once per hold and once per red trunk commit. The error that a failed ledger repeats on every tick notifies nothing, and neither does a commit that waits on a pending run or an attempt deferred with exit 75: a deferred commit notifies only when it fails after 24 hours. The errors a tick repeats without recording a failure (a checkout that fails, more than 50 commits, a tip that does not descend, a file that does not parse) have no ledger to record that they were shown, so they stay in stderr, `last-tick-sweep.json` and the sweep log. The jobs are LaunchAgents in the operator's Aqua session, where osascript needs no permission. macOS names the sender Script Editor, the owner of osascript, and System Settings > Notifications > Script Editor turns the notifications off or makes them alerts that stay on screen; the configuration has no field for them. osascript absent from PATH, a non-zero exit or the cap is the `notification failed` error, and the tick goes on. A notification reaches only this Mac: away from it, it waits in Notification Center, and a Focus holds it until the Focus ends.
